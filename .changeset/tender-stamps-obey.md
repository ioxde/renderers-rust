'@codama/renderers-rust': minor
---

PDAs whose seeds are all constant now answer `find_*_pda()` from constants baked in at generation time instead of deriving at runtime. The renderer already folded such an address into `<PDA>_ADDRESS`, but the generated `find_*_pda()` and the account-inherent `Account::find_pda()` still called `Address::find_program_address`, recomputing a value the binary already carried. On-chain that is the `sol_try_find_program_address` syscall at 1,500 CU per bump attempt — up to roughly 380k CU in the worst case, past the default compute budget — for an answer that cannot vary. Both helpers are now `pub const fn` returning the folded pair, so they are also usable in `const` items, array lengths and other const contexts where a runtime derivation is not. `create_*_pda(bump)` is unchanged: it still derives through `create_program_address`, because it accepts any bump, not just the canonical one.

The bump the derivation stops at is now emitted as `<PDA>_BUMP`, alongside `<PDA>_SIGNER_SEEDS`, a `&[&[u8]]` listing each seed constant in order followed by `&[<PDA>_BUMP]`. It is what `invoke_signed(&ix, &accounts, &[<PDA>_SIGNER_SEEDS])` expects, so a program that signs as one of its own PDAs no longer has to re-derive the bump or hand-assemble the seed slice. Because `AsRef::as_ref` is not a `const fn`, a seed standing for the deriving program renders as `&<program>.to_bytes()`, naming `<PDA>_PROGRAM_ADDRESS` when the IDL pins the program and `crate::<PROGRAM>_ID` otherwise. Every one of `<PDA>_ADDRESS`, `<PDA>_SEED*`, `<PDA>_BUMP` and `<PDA>_SIGNER_SEEDS` comes from the same encoded bytes, so they cannot drift from one another. Nothing is folded where nothing can be: PDAs with variable seeds, and PDAs whose deriving program is only known at runtime, keep their runtime helpers unchanged.

Instruction builders now decide between `crate::pdas::<PDA>_ADDRESS` and `crate::pdas::find_*_pda()` by asking whether the PDA actually folded, rather than by re-testing the conditions that usually imply it. A constant-only PDA that takes more than fifteen seeds, or holds a seed longer than thirty-two bytes, emits no `<PDA>_ADDRESS` — those guards mirror what the runtime derivation itself rejects — yet the builder still read the constant, so the generated crate did not compile. Such PDAs now fall through to the runtime finder beside them.

The PDA page, the account-inherent helpers and the instruction builders now share one decision about which program a PDA derives under, so a folded address cannot be derived under a program the helper beside it never uses. Unifying it settles one case the three had answered differently: a PDA pinned to the very program that renders it, whose every use-site supplies its own deriving program. Codama writes a PDA's `programId` by resolving such a use-site reference against an address-constrained account, so a pin and a reference that coexist name the same address and the pin is that address in statically known form. Any pin therefore beats the use-sites, including one naming this very program: the helpers derive under it, the address folds, and the deriving program is no longer a parameter. Anchor produces this shape from `seeds::program = <account>` wherever that account is address-constrained to the program's own id, which `Program<'info, T>` alone is enough to do.

That decides the builder's argument list as well as the finder's signature, so the two cannot disagree. A self-pinned PDA whose finder now takes no deriving program is no longer passed one — previously the page dropped the parameter in some shapes while the builder kept supplying it, which does not compile — and where such a PDA has variable seeds and nothing to fold, the builder calls the finder with its seeds alone. The runtime program reference the IDL names at the use-site is not read, because the pin already resolved it.
