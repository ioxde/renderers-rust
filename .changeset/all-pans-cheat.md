An IDL-optional account carrying a PDA default no longer breaks the builder. Its `Option` now passes straight through to the accounts struct, so `None` means what the program says it means — the program id, or the account omitted, per `optionalAccountStrategy`.

Previously `instruction()` resolved the PDA default ahead of the optional check, which was wrong three times over. The binding unwrapped to a bare `Address` while the accounts struct field was `Option<Address>`, so any instruction with such an account failed to compile; because the default was always substituted, callers had no way to omit an account the program had gone out of its way to make optional; and `resolveInstructionPdaDefaults` swept every pda-defaulted account, optional or not, into the set of names whose `instruction()` local a later PDA derivation could reference bare — correct only because the `pdaDefault` branch used to win, which is what made that local an `Address` rather than an `Option<Address>`. Letting the optional check win the branch fixed the first two outright, but not the third: once an optional pda-defaulted account's local became `Option<Address>`, any other account whose PDA derives from it — as a dynamic deriving program, as a linked-PDA seed, or as an inline-PDA seed — was still reading that bare local, so `&Option<Address>` stood where `&Address` was wanted, and at the inline-seed site `Option::as_ref()` produced `Option<&Address>` where a byte slice was wanted; both still failed to compile. The set that gates the bare reference now excludes IDL-optional accounts, so a dependent PDA falls through instead to the same field-reading branch every other optional account already uses, unwrapping with `.expect(...)` — `&self.vault.expect("vault is needed for receipt PDA")`, or `&self.vault.map(|(k, _)| k).expect(...)` when the account is an either-signer.

A caller who omits an optional account that another account's PDA derives from now gets that panic when `instruction()` runs. That is the coherent outcome, not a defect: omitting the account means `None` reaches the accounts struct, which drops the account from the transaction or substitutes the program id per `optionalAccountStrategy`, and neither is an address the transaction actually carries, so deriving a dependent PDA from it would be deriving from an address the instruction does not have. A caller who wants the dependent PDA has to supply the account its seed derives from.

Accounts that are merely optional in the builder — required by the IDL, defaulted for convenience — are unaffected and still get their default applied.

Separately, the ed25519 on-curve test used when folding a PDA address at generation time now runs in ZIP-215 mode, matching `curve25519-dalek` and therefore the runtime. Without it the renderer applied the stricter RFC 8032 rules, so a candidate the runtime counts as on-curve could look like a usable address here and fold a constant at a bump `find_program_address` would have skipped.
