'@codama/renderers-rust': major
---

PDA helpers now derive under `pdaNode.programId` whenever the IDL pins one, independently of how the PDA is used. `pdasPage` consulted the pin only for PDAs whose every instruction use-site also supplied a runtime deriving program, so a PDA pinned to a foreign program but used inconsistently — or never used as an instruction account at all — fell through to deriving against the rendering crate's own `<PROGRAM>_ID`. For an all-constant-seed PDA this was visible inside a single generated file: the folded `<PDA>_ADDRESS` constant already honoured the pin while `create_*_pda` and `find_*_pda` beside it derived somewhere else entirely. A pin is answerable at generation time, so it now decides the deriving program before the use-sites are consulted, and the `<PDA>_PROGRAM_ADDRESS` constant is baked in for every pinned PDA rather than only the dynamic-program ones. Unpinned PDAs whose deriving program is genuinely runtime-only keep taking a `program_address` parameter, and unpinned same-program PDAs keep deriving against `<PROGRAM>_ID`.

A `programIdValueNode` seed on an inline PDA is now hashed as the program the address derives under rather than always as the local one. The deriving program and that seed are the same value by construction — Codama resolves both as the runtime reference, then the `pdaNode` pin, then the rendering program — but the instruction builders re-derived the seed independently and always reached for `crate::<PROGRAM>_ID`. A PDA pinned to a foreign program with no runtime reference at the use-site therefore hashed the local program while deriving under the pin, producing an address the program would never accept. This is the Metaplex-metadata shape, whose seeds are `["metadata", <metadata program id>, mint]` derived under the metadata program.

The inherent `Account::create_pda` and `Account::find_pda` helpers on account pages had no notion of the pin at all and hardcoded `crate::<PROGRAM>_ID` both as the deriving program and as the value of a `programIdValueNode` seed. They now follow the same rule as the standalone helpers, so the two agree on the address for a given PDA. The account's owner guards in `TryFrom<&AccountInfo>`, `fetch_all_*` and `fetch_all_maybe_*` are unchanged and still check the rendering program: only the derivation moved. Where an account's PDA has no pin and every use-site supplies its own runtime program, there is no address to compile into an inherent method that takes no program parameter, so the two helpers are omitted for that account instead of being emitted deriving under the wrong one. The rest of the account — struct, discriminator, decoders and fetchers — still generates, a generation-time warning names the account and the PDA, and a doc comment on the struct points at the standalone `crate::pdas::find_<name>_pda`, which takes the deriving program as a parameter.

**Breaking:** after regenerating, any PDA pinned to a foreign program that was not already dynamic-program-only derives a different — and now correct — address, as does any inline PDA that hashes its deriving program as a seed under a pin. Addresses cached or hardcoded from previous output are stale. Pinned PDAs also gain a `<PDA>_PROGRAM_ADDRESS` constant. Accounts whose PDA derives under a runtime-only program lose their inherent `create_pda`/`find_pda`, which previously returned an address derived under the wrong program; call sites move to `crate::pdas::find_<name>_pda(seeds, program_address)` and will fail to compile until they do. Pinning the PDA's `programId` in the IDL restores the inherent helpers.
