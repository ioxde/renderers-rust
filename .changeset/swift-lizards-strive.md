Constant PDA seeds are now encoded once, by a single shared encoder, and the generator refuses to emit a seed it cannot reproduce byte-for-byte. The renderer previously carried two independent encoders for the same seed: `computePdaAddress` produced the bytes hashed into the folded `<PDA>_ADDRESS` constant, while `renderConstantSeedBytes` produced the `<PDA>_SEED` Rust literal that `create_*_pda` and `find_*_pda` hash at runtime. Both ignored the seed's declared type for string, bytes and public-key values, and only the former resolved nested type nodes, so the two agreed by coincidence rather than by construction. Both now call `getConstantPdaSeedBytes`, which accepts only bare type nodes and returns the exact bytes or the reason it cannot; where it cannot, generation fails with a `[Rust] Cannot encode constant PDA seed` error naming the type, the value and the cause, rather than emitting helpers that derive an address the program never accepts.

String seeds are decoded according to their declared encoding. A `stringTypeNode` seed declared `base16`, `base58` or `base64` was previously hashed as the raw text of the literal and rendered as a `b"…"` byte string of that same text, so the seed bytes bore no relation to what the IDL described; only `utf8` was correct by accident. Decoding is validated by re-encoding, because `@solana/codecs-strings` silently pads odd-length base16 and truncates incomplete base64 groups instead of rejecting them, and a codec that invents or drops bytes must not be mistaken for a successful decode. The readable `b"…"` form is now used only for printable-ASCII `utf8` seeds, where it is provably those exact bytes; everything else renders as an explicit byte array. A `utf8` seed containing non-ASCII previously emitted a `b"…"` literal that rustc rejects outright.

Numeric seeds are range-checked before they are encoded. A `u8` seed holding `300` was masked to `44` when folding the address while the seed constant rendered as `&300u8.to_le_bytes()`, which fails to compile, so the two encoders disagreed and neither was right; values outside a format's inclusive range, and non-integers, are now refused. Negative values in signed formats are parenthesised, since `-1i64.to_le_bytes()` parses as a negation of the array and does not compile. Endianness is unchanged: `endian === 'le'` selects little-endian and anything else selects big-endian, matching the templates and `renderValueNodeVisitor`.

Address-shaped seeds and program addresses must decode to exactly 32 bytes, and the guards that Solana's own derivation enforces are applied before an address is folded. A malformed or truncated program address hashed cleanly into a plausible-looking constant for an address that cannot exist; a `publicKeyValueNode` seed of the wrong length did the same. The folded constant is now dropped, leaving the runtime helpers in place, when a derivation takes more than fifteen caller seeds — sixteen is the protocol limit and `find_program_address` spends one on the bump it appends, so at sixteen the runtime raises `MaxSeedLengthExceeded` rather than stepping down to the next bump — or when any single seed exceeds thirty-two bytes. These two cases suppress only the constant, since the seeds themselves are still valid literals and the helpers fail exactly as the on-chain program does.

**Breaking:** an IDL whose constant PDA seed cannot be encoded byte-exactly now fails generation instead of producing a client that derives unreachable addresses. This covers seeds wrapped in `fixedSizeTypeNode`, `sizePrefixTypeNode`, offsets, sentinels and hidden prefixes or suffixes, numeric seeds outside their format's range, public-key seeds that are not 32 bytes, and seeds whose value kind does not match their declared type. Any PDA with a `base16`, `base58` or `base64` string seed, or a `utf8` string seed containing non-ASCII, folds to a different — and now correct — address after regenerating, so addresses cached or hardcoded from previous output are stale. PDAs with more than fifteen seeds, or with a seed longer than thirty-two bytes, no longer emit a `<PDA>_ADDRESS` constant; call sites move to the `find_*_pda` helper beside it.
