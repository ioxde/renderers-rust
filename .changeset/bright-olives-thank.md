Instruction accounts whose address is fixed at generation time are no longer builder inputs. When the IDL pins an account — an `address =` constraint, the program id, a linked program, or a PDA whose every seed and deriving program are known here — the on-chain program enforces that address, so a setter could only ever produce a failing transaction. The plain builder now drops such an account's `Option<Address>` field, its `new()` parameter and its setter, and `instruction()` binds the account directly to the fixed address (an address literal, `crate::<PROGRAM>_ID`, or `crate::pdas::<PDA>_ADDRESS`). Its doc line stays, annotated `(fixed to '…')`, so the list still numbers every account meta. The account still reaches the account metas exactly as before, so the instruction on the wire is unchanged.

This is a breaking change for callers: code that calls one of those setters, or that passes one of those accounts to `new()`, no longer compiles. Delete the call — the address it was setting is the only one the program accepts. Callers who genuinely need to pass a different address should use the low-level accounts struct, which still requires every account and remains the escape hatch; the CPI builder is likewise untouched and still takes every account.

An account is only dropped when every one of the following holds, so accounts that merely look pinned keep their input. It must not be a signer, since `#[account(address = ADMIN)] pub admin: Signer<'info>` pins the address yet still needs a signer from the caller. It must not be IDL-optional, whatever its default: omitting an optional account is a choice the program offers the caller, `None` reaches the accounts struct and emits the program id or drops the account per `optionalAccountStrategy`, and no pinned address can reproduce that meta. The default must have been declared by the program rather than invented from the account's name by Codama's `setInstructionAccountDefaultValuesVisitor`, so an account that only looks pinned — an unconstrained `token_program` that must accept Token-2022, a sysvar or `program_id` that acquired its address from the name rule rather than the IDL — stays parametric. An account the IDL really does constrain is dropped even when it is a sysvar or a token program, because there the address is the program's own requirement. For a `publicKeyValueNode` that means carrying the account's own name as its identifier, which is what a real `address =` constraint produces; the one rule that invents a bare program id instead is recognised by the account name it matched. Nothing else in the instruction may derive from the account, so the associated-token program's `token_program`, which is a seed of the ATA, keeps its input. And an instruction containing a resolver is left entirely alone, since a resolver body is opaque to the renderer.
